# Working Agreement: Confirm Before Building & Hybrid Delivery (Godot)

> Paste this together with `HANDOFF_sekiro_like_prototype.md` at the start of each new chat.

---

## 1. Confirm before building (tiered)

Before writing code or giving scene instructions, Claude replies with an **understanding check** and **waits for an explicit go-ahead**. How much detail depends on the request:

| Request type | Check required |
|---|---|
| **New feature or system** (a build-order step or a major part of one) | **Full check** (below) |
| **Fix or tweak** | **Short check**: 2-3 lines (what's wrong, proposed change, files touched) |
| **Questions, explanations, tiny changes** | **No check**, just answer |

### Full check contains
- The request restated in Claude's own words
- **Scope:** build-order step number(s) from the handoff doc (or "outside the doc")
- **Assumptions and open items** that affect it, each with a proposed default
- **Files** to be created, modified, or deleted
- **Scene and editor changes:** nodes to create, Input Map actions, autoloads, `.tres` resources
- **What is not included**
- Delivery format (see section 2) and zip name if a zip is used

### Rules
- A "go" / "confirmed" / "ok" covers **only** the scope restated in the message right before it. If the scope changes, confirm again.
- If a request is ambiguous, Claude **proposes a default** instead of stacking questions, and ends with a single go/no-go ask.
- Claude does **not assume design decisions**. Anything not in the handoff doc is asked or marked as a placeholder.

## 2. Delivery: hybrid

Claude picks the lightest format that is safe:

| Situation | Format |
|---|---|
| Script of about **150 lines or less** | The **complete file** in the reply |
| Larger script | **Only the changed functions**, with exact placement (e.g. "replace `_physics_process`", "add below `_ready`") |
| A step touching **3+ files** | A **zip** of complete files |
| Tiny change (a value, a line) | A one-line instruction |

### Zip rules (when used)
- Contains only **new or modified** files, each as the **complete file**.
- Real paths relative to the **project root** (the folder containing `project.godot`), so unzipping over the root with overwrite lands files in place.
- No manifest, changelog, or wrapper folder.
- Names: `<project>_<short-description>.zip` for features, `<project>-fix1_<short-description>.zip`, then `-fix2_...` for fixes. Every request gets a **new** zip; names are never reused. `<short-description>` is 2-5 lowercase words joined by hyphens.
- **Cumulative correctness:** Claude's working copy is the last version you sent plus every delivery since. A zip holds the latest full version of each touched file.
- **Your own edits:** if you edit a script yourself, tell Claude or paste the current version so it isn't overwritten. In a **new session**, re-send the scripts relevant to the current step.

### Delivery notes
- The reply that accompanies a delivery is **short**: what's included, editor steps to do, how to verify, files to delete (a zip can't delete).
- Claude states plainly that code is **untested** (it can't run Godot).

## 3. Godot-specific rules

### GDScript
- **Tabs for indentation, LF line endings, UTF-8.** Never mix indentation.
- Typed GDScript throughout.
- Edits are **surgical**: untouched lines aren't reformatted or reordered.

### Scenes (`.tscn`)
- Claude gives **explicit node lists** to build in the editor: node type, name, parent, key properties, and where each script attaches.
- Claude delivers a `.tscn` file **only for trivial scenes**. Hand-editing scene files is fragile.

### Resources (`.tres`)
- Claude delivers an `ActionData` / `EnemyAIData` `.tres` **only the first time** it is created.
- After that, Claude **never overwrites** tuned resources. Value changes come as "change X to Y".

### `project.godot`
- **Never sent whole** (it would overwrite your settings).
- Input Map and autoload changes come as **step-by-step editor instructions** (Project > Project Settings > ...).

### Never touched or shipped
- `addons/**` (third-party code)
- `.uid` and `.import` files, and the `.godot/` folder (generated by Godot)

## 4. Verification (replaces linting and automated tests)

Claude can't run Godot or lint GDScript here, so:
- Every delivery ends with a short **"How to verify"**: what to press or do, and what you should see.
- You run it and **report back** (what happened vs. expected, plus error text from the Output/Debugger panel, and your Godot version: 4.7.2).
- On request, Claude does an **optional read-through** of code for syntax and logic errors.
- Where useful, Claude offers an **optional debug setup** (e.g. a dummy enemy, hotkeys to trigger states, the debug overlay) to make a step easier to test.

---

## 5. Flow

```
Request  ->  Check (tiered)  ->  "go"  ->  Build  ->  Delivery + short reply + how to verify
                                                            |
                                   You test, report back <--+
                                            |
   Bug found?  ->  fix request  ->  Short check  ->  "go"  ->  fix delivery
```

---

## 6. Session hygiene

- One build-order step at a time; confirm it works before moving on.
- Keep replies concise; no long preambles.
- Start a **new chat per step or topic**, and re-send the handoff doc, this agreement, and the relevant scripts.
- At the end of each session, update the **progress checklist** in the handoff doc.
